## The vision (from assessment @ddc39fb — build on it)
Store the MUD engine's actual **Elixir code as Commonplace documents**, loaded + compiled at runtime — extending `SourceDoc.compile` from just verbs to whole **engine modules**. The key insight: **trust-split** — a node-signature on the code-doc decides trusted-compile-and-run vs sandbox/interpret, **reusing the enforce-gate as the code-loading boundary**. This **subsumes CX-z0v7**: escript-vs-serve skew becomes impossible by construction (code is loaded fresh from docs, not baked into a binary).

## Design the FIRST INCREMENT (cruise-sized, proves the concept end-to-end)
Not the whole engine at once. The minimal slice that proves doc→module→running-code works:
- Pick **ONE engine module** to move into a Commonplace doc first — a **leaf, low-blast-radius** module (something the engine can lose/reload without bricking the world; NOT a core supervisor). Which one, and why.
- The **load → compile → cache → run** pipeline for an engine module served from a doc (vs today's compiled-in module). How it extends the existing SourceDoc.compile/UserVerb path.
- The **trust boundary**: node-signed engine-doc = trusted-compile (full authority) vs unsigned = sandbox/refuse. Exactly how it reuses the enforce/local-write-gate as the code-loading gate (the "third use of the trust seam" but for CODE).
- **Hot-reload** on doc-change (edit the module doc → engine picks up new code) — the payoff demo.
- **Failure/rollback**: if a doc-module won't compile or crashes, the engine must NOT brick — fall back to last-good / refuse-load. This is the load-bearing safety property.
