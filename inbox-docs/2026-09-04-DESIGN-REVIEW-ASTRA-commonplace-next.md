# Design review: commonplace-next

Reviewed commit: `4534324173e0c8f7e2844c86da60795c32d93da9`.

**Scope and evidence.** This is a static source review. **MEASURED** below means directly read in this checkout, including executable statements and test definitions; it does not mean a runtime observation. **INFERENCE** identifies my interpretation, predicted consequence, or recommendation. I checked the commit and initially clean working tree, read the composition, Cell, browser, synchronization, storage, authentication and routing paths, and sampled relevant tests. I did not run tests, compile, fetch dependencies, start services, or reproduce failures. Private dependency implementations and the deployed Cloudflare/sidecar configuration were not verified. References use repository-relative paths and line numbers at this commit. Historical assertions in comments and evidence documents are not treated as measurements made by this review.

**Overall judgement — INFERENCE.** The strongest design decision is giving canonical documents, editor-owned mirrors, and browser projections different responsibilities. That creates a credible foundation for durable collaborative editing and keeps cross-realm access behind explicit admission. The weakest part is lifecycle consistency: durable identities coexist with captured process identities, accepted browser sessions outlive the assertions that established them, and several logs and caches have no bounded lifetime. I would stabilize those contracts before broadening the number of organizations, hosted documents, or remote peers. The existing abstractions are useful; adding more packages is not the immediate remedy.

**The architecture and its useful boundaries.**

**MEASURED.** `application.ex:8–27` starts credentials, the gateway listener, a Realm, the HTTP endpoint, and optionally the JWKS source. `realm.ex:48–78` composes the issuer, keystore, routing registry, gateway sessions, workspace Cells and editor Cells. `cell/supervisor.ex:65–91` gives each Cell document hosts and, for editors, a mirror store, mirror supervisor and attachment supervisor. These paths are under `lib/commonplace_next/`.

**MEASURED.** The browser's provider batches Yjs updates into identified author operations (`assets/src/provider.js:151–175`). `yjs/attachment.ex:284–369` submits a conditional content commit to DocHost and acknowledges after a successful receipt, with durable duplicate lookup at lines 265–280. Mirror creation first admits the session, resolves the canonical document and checks its Markdown interpretation (`editor_cell/mirrors.ex:59–78,385–391`). It records an allocation before proceeding through fork, directory entry and mirror index (`439–468`). `MirrorSupervisor` supplies a local child endpoint and a routed canonical endpoint (`editor_cell/mirror_supervisor.ex:62–107`). `Realm.Route` chooses local delivery or the gateway (`realm/route.ex:11–30`); `Cell.Host` plans admission before executing an adapter (`cell/host.ex:132–158,202–221`).

**INFERENCE.** This makes browser replacement, retryable mirror provisioning, storage adapter changes and remote placement easier than they would be in a controller that directly edits canonical state. In particular, operation identity and conditional head selection are valuable foundations for recovery after an uncertain acknowledgement. The price is several interacting lifecycles and two application-level authorization edges. Correctness depends on reconnect, restart and partial completion preserving those distinctions—not just on each individual module having a sensible API.

**1. High priority: the Cell supervision graph does not encode its restart dependencies.**

**MEASURED.** `cell/supervisor.ex:22–35` starts the supervisor, retrieves a `Hosts` PID, then performs provisioning and adds `Host`. The added Host's child specification captures that PID (`129–138`). The supervisor uses `:one_for_all` (`91`). `Host.init/1` retrieves and immediately uses the captured PID (`cell/host.ex:31–47`). Host lookup derives the Cell identity from the supplied hosts process, and its dynamic supervisor lookup calls `Supervisor.which_children(hosts)` (`hosts.ex:257–274`). `ensure_mirrors/1` is called by the outer start function through `provision_and_start_host/3`, not by `MirrorSupervisor.init/1`; that init only creates an empty DynamicSupervisor (`editor_cell/mirror_supervisor.ex:14–20`).

**INFERENCE, high confidence in the structural defect; failure not reproduced.** When a Store or other direct child fails and `:one_for_all` restarts siblings, the saved Host child specification still names the old Hosts PID. Restarting the existing supervisor's children does not rerun its outer `start_link/1` provisioning sequence. I expect failed Host restarts and possible escalation to a whole-Cell restart; durable mirrors also lack an explicit rehydration step on this internal restart path. A later whole-Cell restart may recover, but relying on restart escalation is a poor recovery contract. The Realm restart test at `test/commonplace_next/realm_test.exs:418–425` exercises rebuilding the whole Realm, which is a different path.

**INFERENCE / recommendation.** Make restart specifications depend on stable Cell IDs or registered names, resolve current processes during child initialization, and put mirror rehydration in a supervised startup phase. Specify separately what must recover after a DocHost, Store, Hosts supervisor, and entire Realm failure. There is also a deliberate availability tradeoff: `DirectoryIssuer` is `:temporary` (`realm/directory_issuer.ex:65–70`) and returns `:issuer_unavailable` when absent (`291–294`). That avoids independently rotating the key underneath the keystore, but issuer death leaves issuance unavailable until coordinated recovery. Preserve key coherence while making that recovery and readiness state explicit.

**2. High priority: the browser projection has a second, non-durable mutation path.**

**MEASURED.** `Web.YjsSocket.handle_in/2` forwards decoded binary frames to the attachment (`web/yjs_socket.ex:27–36`). `Attachment.apply_frame/3` accepts both Yjs `step2` and `update`, applies them to `state.doc`, and broadcasts them without a DocHost call (`yjs/attachment.ex:209–215`). In contrast, the author envelope passes epoch, size, operation-ID and durable commit handling (`200–205,236–320`). The repository's browser sends authored changes through the envelope; its sync reply encoder is not sent (`assets/src/provider.js:138–141,158–175`). Tests explicitly send binary updates and assert peer propagation and reconnect diffs (`test/commonplace_next/yjs/attachment_test.exs:557–592`). These are test definitions, not results from this review.

**INFERENCE.** An authorized custom client can make other clients see content that has no corresponding durable content head. Rebuilding the attachment from DocHost can then remove that content. A later authored edit may also refer to Yjs structures only present in the projection, making the durable validation boundary harder to reason about. This is not evidence of an unauthenticated write or of a canonical-storage bypass; it is a split between visible and durable truth inside an authorized mirror.

**INFERENCE / recommendation.** Make client-to-server content mutation enter through one durable authoring path. Reject mutating binary sync frames, or explicitly adapt them into an equally validated durable operation. Keep state-vector requests and server-to-client diffs. Tests should distinguish “another browser displayed it” from “a fresh attachment rebuilt it from storage.” The current browser already largely follows this separation; the server should enforce it.

**3. High priority: authentication establishment is stronger than authentication lifetime.**

**MEASURED.** Assertion verification checks key, signature and claims and constructs an identity carrying expiry (`cloudflare_access/assertion_verifier.ex:51–74`). But failed verification leaves the connection unchanged (`web/access_authentication.ex:55–64`). `Session.authenticated?/1` calls `entry/1`, which resolves the login from the signed cookie (`web/session.ex:512–527`). The socket routes do not use the browser authentication pipeline (`web/router.ex:64–70`); the upgrade fetches the session and checks cookie-derived login and mirror ownership (`web/page_controller.ex:114–133`, `web/session.ex:551–575`). Socket state contains no assertion expiry, and its frame handlers perform no identity refresh (`web/yjs_socket.ex:14–69`). The cookie configuration supplies a store, key and signing salt, but no application-level identity expiry (`web/endpoint.ex:6–10`). Production does require an external session secret (`config/runtime.exs`, production endpoint configuration).

**INFERENCE.** A legitimately established cookie is an independent credential at the socket boundary. The application itself does not tie subsequent editing to the lifetime of the verified assertion or periodically re-resolve membership on a live socket. This may be acceptable if an upstream service enforces the desired lifetime for every relevant connection, but that deployment assumption is not established here. I have not tested expired assertions, revoked memberships, stolen cookies, or Cloudflare's treatment of existing sockets, and do not claim the production site is externally bypassable.

**INFERENCE / recommendation.** Specify the revocation and expiry contract for both upgrades and established sockets. Carry the verified identity and expiry into the socket authorization decision, or introduce an explicit application session with renewal and revocation semantics. Avoid treating an invalid assertion as equivalent to an absent assertion when a prior session exists without a deliberate policy. Also define freshness for verification keys: `KeySource` returns cached keys immediately and only refreshes on a miss (`cloudflare_access/key_source.ex:160–203`). Its refresh interval bounds miss-triggered fetches; it is not a maximum age for a cached key. Removal of an already cached key is therefore not necessarily noticed until a miss or restart. This is another lifetime decision, separate from signature verification correctness.

**4. High priority for growth: a Cell is one synchronous execution queue with unlimited response retention.**

**MEASURED.** All `Host.deliver*` calls use `GenServer.call(..., :infinity)` (`cell/host.ex:15–25`). Admission and adapter execution run inside the Host callback (`77–105,132–158,202–226`). The response map starts empty and stores every admitted-path response by request ID, including refusals; this module contains no eviction (`65–66,158`). Requests are commonly assigned fresh IDs (`realm/router.ex:19`, `doc_sync/cell_endpoint.ex:77–78`). The attachment separately retains operation IDs, complete update bytes and heads in `authored`, without eviction during its lifetime (`yjs/attachment.ex:57,344–362`).

**INFERENCE.** The workspace Cell serializes work across its documents even though the documents have separate hosts. One slow storage operation can delay unrelated requests. Host memory grows with request history, including read traffic, and attachment memory grows with editing history while clients keep it active. I have not measured bytes per request or throughput; no capacity number follows from these observations. Restart clears Host retention, so this cache is also not a durable exactly-once guarantee.

**MEASURED.** The gateway starts a task per accepted connection without a configured concurrency cap (`realm/gateway.ex:62–91`). Its deadline helper closes a socket and sends an expiry message, but executes the callback synchronously in the caller (`realm/gateway/deadline.ex:18–30,118–120`). Ordinary dispatch waits for `Host.deliver_bytes/3` (`realm/gateway.ex:770–773`).

**INFERENCE / recommendation.** A socket deadline is not cancellation of queued or executing Cell work; a timed-out caller may still have an effect committed later. Define bounded admission queues, execution deadlines and uncertain-result retry semantics together. Preserve per-document ordering while allowing independent document work where the admission contract permits it. Bound response and authored-update caches using an explicit retry window, retaining durable operation lookup for retries beyond memory retention. Rate and connection limits should complement payload-size limits.

**5. Medium-high priority: “durable journal” currently has several different meanings.**

**MEASURED.** The Journal behavior requires durability before returning `:ok` (`doc_sync/journal.ex:23–24`). Store appends before updating memory and replying, and stops on append failure (`doc_sync/store.ex:113–120`): this is good ordering. However, the local adapter uses `File.open(..., [:append, :binary], &IO.binwrite/2)` with no explicit file synchronization (`doc_sync/journal/file.ex:40–48`). It reads the complete file at startup (`52–59`). The log adapter replays all pages from cursor zero (`doc_sync/journal/log.ex:48–78`). Store holds the folded map in memory (`doc_sync/store.ex:37–42`). Neither journal adapter exposes compaction through the behavior.

**INFERENCE.** The file implementation does not establish power-loss durability merely by completing a write and closing the file; its contract should distinguish process restart from machine/storage failure. This local path is for development and tests, so it is not evidence that the production sidecar fails to persist. Conversely, local reopen tests cannot establish the sidecar's acknowledgement guarantee. Complete-history replay also makes restart cost grow with all mutations, including overwritten values, rather than just current relationships. A damaged tail deliberately prevents startup (`doc_sync/journal/file.ex:75–89`), which protects against silent partial recovery but needs a repair procedure.

**MEASURED.** Values are base64-encoded Erlang terms, decoded with unrestricted `binary_to_term/1`, with no format version (`doc_sync/journal.ex:65–86,107–129`). Those same values pass through the sidecar adapter, not only a local file. `Journal.Log.open/1` treats every open error as a reason to try creating the log (`doc_sync/journal/log.ex:29–36`).

**INFERENCE / recommendation.** Define durability guarantees per adapter; add safe checkpoint/compaction and repair semantics; version the stored value schema before dependency changes require migration. Treat sidecar content as a trust boundary: opaque terms couple persistent data to Elixir module/struct shapes, and unrestricted decoding can create atoms if storage is hostile. I did not establish an attacker-controlled route into this storage. Distinguish “not found” from transport, authorization and corruption failures before attempting creation. Whether the dependency currently makes that fallback harmless is unverified.

**6. Medium-high priority: identifiers support multiple organizations, but the application context still selects one.**

**MEASURED.** `Realm.start_for/1` can add another organization's workspace (`realm.ex:34–44`), and `WorkspaceCell.descriptor/1` and `config/1` accept an explicit organization (`workspace_cell.ex:66,95`). Nevertheless, mirror startup always uses `WorkspaceCell.descriptor/0` (`editor_cell/mirror_supervisor.ex:62–78`); gateway serving looks up that same primary workspace (`realm/gateway.ex:147`); mirror ownership reconstructs keys with it (`web/session.ex:568–573`). The URL coordinate plug compares the requested organization to `Organization.configured/0` and rejects differences (`web/organization_coordinate.ex:76–82`); it does not select a tenant. Editor roster enumeration derives the initial membership generation from configuration (`organization/editor_placement.ex:76–83`), and both login and Cell-ID lookup use that enumeration (`90–127`).

**INFERENCE.** This is a single-primary-organization application with some multi-organization construction primitives, not end-to-end multi-tenancy. The explicit URL guard is useful and avoids pretending otherwise, but simply allowing a second coordinate would leave downstream operations targeting the primary. Membership generation changes would also require changing configuration-based placement resolution. The source comments acknowledge these constraints; they remain significant design limits rather than evidence that the follow-up work is complete.

**INFERENCE / recommendation.** Before serving a second organization or implementing membership regeneration, introduce one explicit resolved context containing organization, workspace, member generation and editor identity, and carry it through session, routing, mirroring and ownership checks. Remove primary defaults from those internal paths together. Keep convenience defaults only at deliberately single-organization entry points.

**7. Medium priority: mirror orchestration reaches through boundaries and diagnostic work can amplify load.**

**MEASURED.** `MirrorSupervisor.mirror/2` scans all children and calls `:sys.get_state/1` to inspect each dependency Mirror's `options` map (`editor_cell/mirror_supervisor.ex:46–57`). `Mirrors.status/2` calls `ensure/2` and then `Mirror.status/1` (`editor_cell/mirrors.ex:85–101`), so a status read may start a mirror. Each content-change notification schedules three status refreshes; publishing starts a linked task, with no in-flight guard or result sequence (`yjs/attachment.ex:123–138,503–529`). By comparison, checkpoint work explicitly tracks `in_flight` and ignores stale timer tokens (`checkpoint/worker.ex:69–89,103–119`).

**INFERENCE.** Status lookup becomes a sequence of synchronous introspection calls as relationship count grows. One slow mirror can delay finding another, and a dependency's private state layout becomes part of the application's effective API. Status tasks can accumulate during slow synchronization and complete out of order, presenting stale status after newer status. These are predicted load and ordering effects, not benchmark results.

**INFERENCE / recommendation.** Register mirrors by `{editor_id, relationship_id}` and look them up directly. Separate observation from activation where possible. Apply the checkpoint worker's explicit in-flight discipline to status sampling, coalesce refresh requests and discard obsolete results. Diagnostics should remain cheap during the failure they are intended to explain.

**8. Medium priority: browser reconnect support is not a durable offline-editing contract.**

**MEASURED.** The provider keeps pending operations and local updates only in a Map and array (`assets/src/provider.js:33–35`). It resends pending IDs on reconnect (`88–98`), deletes them on acknowledgement, and leaves them pending on refusal (`115–120`). A reload request blocks if edits are pending (`121–125`). Local batching resets its 50 ms timer on every update and only flushes while connected (`151–167`). Destroy closes the socket without persistent storage or a flush (`185–189`).

**INFERENCE.** Reconnect within a surviving page is supported, but closing or reloading a page can lose unacknowledged edits. Continuous updates can postpone the debounce flush, and a long offline interval can produce one merged update larger than the server's authored-update limit. A refusal has no explicit correction, discard or rebase path in this provider. The distinct `local`, `saving` and `saved` labels are helpful; they do not themselves preserve pending data.

**INFERENCE / recommendation.** Decide whether pending edits must survive page loss. If so, persist operations before sending, preserve IDs across reloads, and provide recovery for refused operations. Independently add a maximum batching delay and a payload policy coordinated with server limits. Do not imply offline durability from in-memory retry alone.

**9. Medium priority: library separation is real, but contract ownership and source-level guardrails impede evolution.**

**MEASURED.** `mix.exs` pins the Commonplace libraries to Git revisions with overrides. Yet `EditorCell` owns directory/document contract schemas and digest constants (`editor_cell.ex:44–350`); `Mirrors` reaches into `WorkspaceCell.config/0` and examines its authorization callback, trust-store contents and contract shape before routing (`editor_cell/mirrors.ex:322–346`). `CellEndpoint` has compatibility clauses that wrap routed endpoints in a dependency's `Local` shape (`doc_sync/cell_endpoint.ex:84–96`). The gateway invokes membership resolution in `Web.Session` (`realm/gateway.ex:251–254`, `web/session.ex:128–145`).

**INFERENCE.** Package direction is cleaner than responsibility direction. Transport, domain authorization, application composition and Web session concerns still know each other's details. This makes a new verb or dependency bump a coordinated edit across several layers. I would extract shared domain membership/admission resolution from Web, make protocol-contract ownership explicit, and replace the endpoint-shape workaround when the dependency supports the appropriate abstraction. This calls for clearer internal interfaces, not necessarily additional repositories.

**MEASURED.** Source shape also influences implementation: `cell_endpoint.ex:118–122` documents a parser-sensitive function head, `web/session.ex:428–432` says even a comment can affect principal-sink counting, and `yjs/attachment.ex:474–476` constructs a function atom and calls `apply/3` for snapshot-and-watch. Some comments are visibly stale: `web/session.ex:34–39,184–193` describes a committed shared session secret and retained development behavior, whereas production now fetches its secret and the credentialless routes are absent. `README.md`'s opening status is explicitly measured at an older commit.

**INFERENCE.** Negative controls and explicit evidence limits are valuable, but text inventories can reward preserved spelling rather than a preserved security property. Stale incident narratives mixed into live contracts make it harder to determine the current rule. Keep inventories as supplemental checks, use syntax-aware inspection where static enforcement is needed, and prefer boundary-level acceptance/refusal tests for authority. Keep current invariants beside code and move historical explanations to referenced records. I did not run any gate and do not independently endorse the historical pass counts.

**Recommended sequence — INFERENCE.** First make internal Cell restart and durable browser mutation invariants unambiguous. In parallel planning, settle socket/session expiry and the storage acknowledgement contract. Then bound request retention, execution queues, status work and replay cost. Only after those contracts are explicit should organization selection and membership-generation changes spread through the application. Future focused verification should include a direct Store-child failure, projection rebuild after a binary sync mutation, an established socket across identity expiry, a queued request whose client deadline expires, and journal replay across an upgrade. These are proposed checks; none was executed for this review.
